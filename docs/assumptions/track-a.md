# Track A assumptions, interpretations and SPEC defects (SPEC v1.1)

Track A = ZK reference circuit (`circuits/`), `@merces/sdk`, `@merces/reference` (bigint math +
simulator) and the parity vectors (`packages/vectors`, schema 2, `specVersion: "1.1"`). Every default,
reading and defect found while implementing SPEC.md v1.1 is listed here with the section it concerns, so
the lead can fold it into `ASSUMPTIONS.md` / fix the spec. "Vectors follow" says what the parity vectors
encode today.

## SPEC defects (money or liveness semantics; the brief wins)

| # | Section | Status in v1.1 | Defect | What the reference does | Vectors follow |
| --- | --- | --- | --- | --- | --- |
| S1 | §6.3 `vault_receive_gross` (also §6.8 tail carry, §6.9 final carry) | **fixed in SPEC text by the lead after this report** (`carry_wad`, `tail_carry_wad`, `final_carry_wad`) | `delta_acc = floor(net × WAD / N); distributed = floor(delta_acc × N / WAD); carry = net − distributed` re-adds a whole base unit that the accumulator already represents (all but `(net × WAD mod N) / WAD` of it). After a few distributions `floor(net_acc × N / WAD)` exceeds the vault balance: N = 3, three net payments of 1 → a single holder can claim 4 of 3. Violates brief C2 ("never lets holders be paid more than the vault holds") and F2 ("total claims never exceed vault balance"). The v1.1 "separate carries" for tail/final inherit the same formula. | Exact WAD-scaled remainder, one per accumulator: `num = net × WAD + carry_wad; delta_acc = floor(num / N); carry_wad = num − delta_acc × N` (`0 ≤ carry_wad < N`, fits u64). Then `acc_wad × N + carry_wad == Σ net × WAD` exactly, so claims never exceed the balance. The ledger field is `carry_wad`; the vectors expose both `ledger.carryWad` and the spec's `ledger.carry = floor(carryWad / WAD)`. Regression test: `packages/reference/test/vault.test.ts`. | Every vector that distributes payouts has 400 units outstanding (vector 03 sells 298 units but never pays; vector 15 sells none) and 400 divides 1e18, so the spec's literal formula yields identical numbers (`carry` is 0 everywhere) and both readings pass today. Fix the spec text anyway; Tracks B/C should implement the exact remainder. |

Nothing else (finalization, releases, accrual, claims) waits for delivery. | Vector 17. |

## Interpretations and defaults (record in ASSUMPTIONS.md)

| # | Section | Reading |
| --- | --- | --- |
| A-1 | §1.5, §8, brief C3 | `income_ytd`, `theta` (and the tier-1 router's `theta`) are expressed in the income currency at the **stablecoin's decimals** (6 for USDC/USDG), so `fx_avg_wad` is a pure WAD ratio and equals `1e18` for stablecoin income as §6.2 step 4 requires. ISO minor units (cents) are an off-chain presentation concern. |
| A-2 | §8, §1.1 | The circuit range-checks the quotient of each `floor(·/WAD)` to 128 bits and `payment_usd` to 64 bits (`Num2Bits(64)`, 3,432 constraints); the chain additionally applies the §1.1 entry-point range rule (`AmountOutOfRange`) to every u64 argument. Products stay `< 2^192`, so no field wrap is possible. |
| A-3 | §8, dev ceremony | The ceremony uses snarkjs **beacon** contributions (SHA-256 hash chain over a fixed public string, 2^10 iterations) for both powers-of-tau and phase 2, making every artefact byte-reproducible. Not a secure setup; `circuits/build/README.md` says so. |
| A-4 | proofs in vectors | Groth16 blinding scalars `(r, s)` are derived from `keccak256("MERCES_DEV_PROOF_RNG_V1" ‖ canonical inputs ‖ nonce)` so `pnpm vectors` is deterministic. The derivation includes the private salts, so proofs stay zero-knowledge towards verifiers; `proveReport(…, { deterministic: false })` gives CSPRNG randomness. |
| A-5 | groth16-solana `vk.rs` | `nr_pubinputs` is written as `IC.len()` (= public inputs + 1), the convention of the crate's own `parse_vk_to_rust.js`; the verifier only uses `vk_ic.len()`. `NR_PUBLIC_INPUTS = 6` is exported alongside. `proofA` in the vectors is already negated (`x ‖ q − y`); the program must not negate again. |
| A-6 | §5.2 settlement steps | A vector `begin_settlement` step carries the proposal and both claims; `finalize_settlement` tallies every revealed bid (all pages) and either settles, fails or **records** a rejection (`auction.roundRejected`, `auction.rejectionReason ∈ {ClaimMismatch, InvalidClearingPrice}`) without reverting. `begin_settlement` during a round that is neither finalized nor rejected reverts `TallyInProgress`; after `Failed` or `Settled` it reverts `RaiseNotOpen`. |
| A-7 | §5.2 two-phase bids | `process_bid` registers the winner as a holder, mints the allocation to the auction escrow and keeps the refund in the auction escrow (`pendingRefund` stays inside `auction.escrowTotal` until `deliver_bid`); `deliver_bid` is permissionless, requires `processed`, reverts `AlreadyDelivered` on repeat. The last `process_bid` finalizes the mint (`unitsMinted == unitsSold` asserted) and stores `units_outstanding`; a failed raise with no bid at all is finalized by `finalize_settlement` itself. |
| A-8 | §5.3 / §6.1 gate | `claim_release`, `submit_report`, `pay`, `submit_trueup`, `pay_trueup`, `retire_if_capped`, `redeem`, `extinguish`, `open_window` revert `MintNotFinalized` before any other check (vector 18). Zero releasable amount reverts `NothingVested`. `settlement_ts` is the block time of the successful `finalize_settlement`; `first_period = period_of(settlement_ts)`. |
| A-9 | §3.2, §6.3 live cap | `cap_per_unit()` is recomputed at every use from the current `cap_multiple_wad`; `expect.ledger.capPerUnit` is that live value (0 before settlement). An amendment does not reset the YTD chain: the next report proves against the new terms commitment with the same `prior_income_commitment`, so the amended θ applies to marginal income only (vector 14; a proof built against the old commitment is `InvalidProof`). |
| A-10 | §6.2 step 7 | Tier 1 and tier 4 reports carry no attestation; a supplied one is ignored. Tier 2 requires an active verifier key, tier 3 an active attestor. A revoked key still validates reports of periods that ended before `revoked_at`, for `report_due_days + grace_days` after revocation (§3 forward-only revocation with grace). The simulator models "signature by registered key X" by actor name; harnesses sign the §1.4 message with the key derived from the vector's `keys[X].seed`. |
| A-11 | §6.2 step 4 | A fallback signature supplied while the accumulator average is valid is rejected (`FxFallbackNotAllowed`); a missing one when `NeedsFallback` is `FxFallbackRequired`; a stablecoin series requires `fx_avg_wad == WAD` and no fallback. The rate carried by a fallback report is whatever the attestor signed (the vector states it). |
| A-12 | §6.2 step 5 | First report of a series whose `first_period` is not a year start: the chain accepts the prior commitment supplied with the report (bound by the attested report message) and the proof must open it (`prior_income_ytd` = attested YTD at `period_start(first_period)`); vector 04 (S2). A first report at a year start, and every report after a year reset, uses the ZERO commitment. Chaining requires `last_income_period == period − 1` in the same year. |
| A-13 | §6.6 checkpoints and coverage | A period checkpoint is created by the first snapshot inside that period; `quarter_average(p)` uses checkpoint `p+1` when stored and the live totals otherwise (so a quarter can be reported right after it ends). Coverage is `n / trading_days_in_period(p)` with Mon–Fri trading days (`tradingDaysInPeriod` in the SDK; counts in `known_answers.json`); the chain accepts at most one snapshot per UTC day on any day (`SnapshotAlreadyTaken`, checked before price validity) and the keeper convention — followed by vector 13 — is to snapshot on trading days only. `StalePrice` (also for non-positive prices) / `ConfidenceTooWide` as §6.6. Pairs are write-once (`FxPairExists`), identified by `keccak256(feed_id ‖ inverted_u8)`. |
| A-14 | §6.6 on Solana | The cross-check feed is modelled as an optional second normalized rate on the snapshot step (`crosscheckPrice/Expo`); pairs created with `crosscheck: false` ignore it (ASSUMPTIONS A21). A >2% deviation flags the period (`NeedsFallback`). |
| A-15 | §6.9 | `extinguish` is allowed in every non-Extinguished status; `unreleased = proceeds − vested(now)` is moved to the final distribution; the issuer's estate keeps claiming what had vested by `extinguished_at`. On a Redeemed series inside its tail the tail ends; final weights are `redeemed_units` for holders who redeemed and unit balances otherwise. `claim_final` settles an unclaimed redemption first, then pays the final share and burns remaining units. |
| A-16 | §6.7 | The redemption gate is: lockup over, status not Late (including `is_late_underlying`), nothing due (`PaymentOutstanding`, true-up included), every ended period since `first_period` reported (`UnreportedPeriods`). `claim_redemption` records `redeemed_units` the first time a holder with units claims; pending payouts are paid together with the redemption price. `C_rem` saturates at 0; a series whose `C_rem == 0` retires instead of redeeming. |
| A-17 | §7 `open_window` | All preconditions other than `WindowsDisabled`, `LockupActive` and `WindowOpen` revert with the single error `WindowNotEligible` (the window must follow the just-reported quarter). One order per wallet per window, either side (`OrderExists`); asks are armed escrow deposits (holder settled first, units moved to the window escrow, accrual weight unchanged). |
| A-18 | §7 `process_orders` | One step processes every order. Buyers are re-checked against the allowlist at fill: a cancelled buyer is refunded in full and the units it would have bought stay with the sellers, taken back from the asks at p* in descending reveal index first, then from asks below p* (the spec names the re-check but not where the units go). Bids above p* fill fully, bids at p* first-come in reveal order (supply-limited); asks below p* fill fully, asks at p* first-come (demand-limited). A proposal at a price with no valid supply or demand is rejected (`InvalidWindowPrice`, recorded). |
| A-19 | §6.5 before finalization | Router receipts that arrive before `mint_finalized` are held in the router's receiving account (`expect.routerBalance`, `IncomeHeld`) and routed together with the next receipt after finalization (vector 18). Tier-1 "split" series with tier 2/3 enabled must report with an attested tier (`TierNotEnabled` for tier 1). |
| A-20 | §6.2 step 8 | Router credit is consumed before the due amount is computed (`credit_used = min(router_credit, payment_usd)`); a report whose due is zero is paid on acceptance (`last_paid_period = period`). On a Redeemed series `pay` is the tail distribution (`tail_receive`, `<` boundary, `tail_exhausted`). |
| A-21 | §6.4 | `expect.ledger.pausedTotal` is the stored `paused_total` (the full approved span, reduced by `end_pause`); `pauseCount` the number of recorded pauses. Countdowns use `unpaused(start, now)` per obligation, so a pause approved while Late stops the accrual clock but releases stay blocked until the arrears are paid (vector 19) and obligations starting after the pause are unshifted (vectors 08, 19). `approve_pause` bounds: `PauseTooLong` covers both the single and the cumulative limit; `TooManyPauses` at `max_pauses` (16). |
| A-22 (anchor amended by the lead, 9 Oct: true-up payments are bucketed by `deadline(period_of(trueup_attested_at))`, the SPEC/Solana/EVM reading — B-S14) | §6.2 true-up | `submit_trueup` carries `nonce`, the `trueup_nonce` the attestor signed over; the chain requires its stored nonce (`InvalidAttestorSignature` otherwise), then increments it, so a replayed signature fails. Checks in order: issuer, mint finalized, tier 3 enabled, attestor active, nonce, `i64` range of the adjustment, `TrueUpOutstanding`, `TrueUpYearInvalid` (already trued up / year not complete / a period of the year unreported since `first_period`), `TrueUpAdjustmentTooLarge` (|negative| > Σ accepted `payment_usd` of the year). A negative adjustment becomes `router_credit`; a positive one is due within `trueup_days` (60) of unpaused time from `attestation_ts`, then the series is Late (releases blocked, redeem `SeriesLate`) and `pay_trueup` adds `late_accrual_trueup` (vector 20). The true-up payment's year_gross anchor is `trueup_attested_at`. `expect.ledger` exposes `trueupNonce`, `trueupDue`, `trueupAttestedAt`, `lastTrueupYear`. |
| A-23 | §11 | Error names used by `expect_revert` are the canonical v1.1 list in `@merces/sdk` `errors.ts` (exported with one-line meanings) and in `packages/vectors/README.md`; `ERROR_ALIASES` maps the v1.0 names (`SeriesTerminal`, `TailExpired`, `NothingToRelease`, `NotLiquidityEvent`). Where several preconditions fail at once a vector pins the reference's check order, which follows the order the SPEC lists them (e.g. §6.2's numbered steps); the vectors avoid such steps elsewhere. |
| A-24 | §11 | `expect` snapshots list every funded actor's stablecoin balance (and unit balance for the step's series), the series' treasury / vault / auction-escrow / router / window-escrow balances, the global fee collector, a fixed `ledger` view, the `auction` round state, the `window` state and `holders[*]` (`pending`, `redeemedUnits`, `pendingUnits`, `pendingRefund`, `delivered`); field lists in `packages/vectors/schema.json`. Harnesses assert every field present. |
| A-25 | §11 keys | Attestor / verifier keys are secp256k1 test keys derived as `keccak256("MERCES_TEST_KEY" ‖ seed) mod (n−1) + 1`; the vector lists seed, private key and address. Bid salts and Poseidon salts derive from the vector name. Nothing in the vectors is a secret. |
| A-26 | §1.4 messages | `MERCES_REPORT_V1` = domain ‖ series_key ‖ period_u32 ‖ prior_income_commitment_32 ‖ income_commitment_32 ‖ tier_u8 ‖ liquidity_event_u8; `MERCES_TRUEUP_V1` carries `trueup_nonce_u64` right after `series_key`. Byte-exact pre-images for a Solana and an EVM test domain are in `known_answers.json`. |

| A-27 | §1.1 zero-amount rule | A claim whose stablecoin and unit amounts are both zero succeeds as a no-op (`claim` with nothing pending, a second `claim` on a Retired series after the units burned); `burn_retired` on an empty or never-registered wallet is a no-op; `pay` / `pay_trueup` / `claim_release` with nothing due or vested still revert (`NothingDue`, `NothingVested`) because they are not claims (vector 21). |
| A-28 | §1.1 entry-point range rule | Every supplied amount, price, quantity, escrow, `payment_usd`, `fx_avg_wad`, timestamp (`pause_end`, `attestation_ts`) and the `i64` adjustment are range-checked first, before any state precondition (`AmountOutOfRange`); a claimed `payment_usd ≥ 2^64` is rejected before the proof is read (the circuit cannot prove it either). Vector 21 covers bid escrow/price/quantity, `pause_end` and `payment_usd`. |
