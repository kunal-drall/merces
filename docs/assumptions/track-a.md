# Track A assumptions, interpretations and SPEC defects

Track A = ZK reference circuit (`circuits/`), `@merces/sdk`, `@merces/reference` (bigint math +
simulator) and the parity vectors (`packages/vectors`). Every default, reading and defect found while
implementing SPEC.md is listed here with the section it concerns, so the lead can fold it into
`ASSUMPTIONS.md` / fix the spec. "Vectors follow" says what the parity vectors encode today.

## SPEC defects (money or liveness semantics; the brief wins)

| # | Section | Defect | What the reference does | Vectors follow |
| --- | --- | --- | --- | --- |
| S1 | §6.3 `vault_receive_gross` (also §6.8, §6.9 "carry as usual") | `delta_acc = floor(net × WAD / N); distributed = floor(delta_acc × N / WAD); carry = net − distributed` re-adds a whole base unit that the accumulator already represents (all but `(net×WAD mod N)/WAD` of it). After a few distributions `floor(net_acc × N / WAD)` exceeds the vault balance: N = 3, three net payments of 1 → a single holder can claim 4 of 3. Violates brief C2 ("never lets holders be paid more than the vault holds") and F2 ("total claims never exceed vault balance"). | Exact WAD-scaled remainder: `num = net × WAD + carry_wad; delta_acc = floor(num / N); carry_wad = num − delta_acc × N` (`0 ≤ carry_wad < N`, fits u64). Then `net_acc_wad × N + carry_wad == Σ net × WAD` exactly, so claims never exceed the vault. The ledger field becomes `carry_wad` (the vectors' `ledger.carryWad`). Regression test: `packages/reference/test/vault.test.ts`. | The fixed semantics. Every vector that distributes payouts has 400 units outstanding (vector 03 sells 298 units but never pays), and 400 divides 1e18, so the spec's literal formula yields identical numbers and both readings pass today; fix the spec text anyway. |
| S2 | §7 `finalize_window` | The supply-limited rule `d_above < S ≤ D` has no solution when sellers offer more units than buyers take at every price (ask 8×5, bid 10×1), and `NO_MATCH` is then invalid too (`max_bid ≥ min_ask`): escrow is stuck with no valid proposal. Also when `S(p) ≤ D(p)` but `d_above == S` (all demand above p*, nothing marginal) no price passes. | Adds the mirror branch *demand-limited*: `D > 0 ∧ s_below ≤ D ∧ D < S` (non-strict on `s_below`), matched = `D`, asks at p* get `floor((D − s_below) × q / s_at)`, unmatched remainder cut from bids at p* (then above) in descending reveal index. Exactly one price or NO_MATCH is valid for every book (3,000-case property test). Supply-limited path unchanged. | Only supply-limited cases (spec as written), so Tracks B/C pass with the current text; the demand-limited rule is proposed spec text. |
| S3 | §7 `return_dust` | "returned to the asks at p*" is impossible when no ask sits exactly at p* (asks 1×5; bids 2×3, 2×3 → U = 1, `s_at = 0`). | Dust goes to asks with `price ≤ p*` in descending price, then descending reveal index (reduces to the spec rule when asks at p* hold enough units). | Vector 10 keeps asks at p*, so the spec rule applies verbatim. |
| S4 | §5.2 `finalize_settlement` | Validity rule (a) `q_at > 0` can never be met when there is no valid revealed bid (nobody revealed, or all reveals invalid): the raise could never finalize and escrow would be stuck. | With no valid bids the proposal `clearing_price = 0` is accepted and the raise fails: full refunds, no fee, no non-reveal charge (ASSUMPTIONS A1: failed auctions charge nothing). | Vector 02 includes this case (`settle` with `clearingPrice: "0"` → Failed). |
| S5 | §6.2 step 2 (tail reports) | For a Redeemed series the text replaces the period sequencing by "liquidity_event && within tail", leaving the period of a tail report undefined while step 5 still chains the prior commitment by period. | Tail reports keep the sequential rule: `period == next expected`, `now ≥ period_end(period)`, no open due; plus `liquidity_event == true`, `now ≤ redemption_ts + tail_seconds`, `tail_cap_per_unit > 0` (`NoTailDue`). `units_outstanding` public input = `units_at_redemption`. | Vector 09. |

## Interpretations and defaults (record in ASSUMPTIONS.md)

| # | Section | Reading |
| --- | --- | --- |
| A-1 | §1.5, §8, brief C3 | `income_ytd`, `theta` (and the tier-1 router's `theta`) are expressed in the income currency at the **stablecoin's decimals** (6 for USDC/USDG), so `fx_avg_wad` is a pure WAD ratio and equals `1e18` for stablecoin income as §6.2 step 4 requires. ISO minor units (cents) are an off-chain presentation concern. |
| A-2 | §8 | The circuit range-checks the quotient of each `floor(·/WAD)` to 128 bits exactly as written; `payment_usd` is therefore `< 2^128` in-circuit and the u64 bound is enforced where the value enters the chain (§1.1). Products stay `< 2^192`, so no field wrap is possible. |
| A-3 | §8, dev ceremony | The ceremony uses snarkjs **beacon** contributions (SHA-256 hash chain over a fixed public string, 2^10 iterations) for both powers-of-tau and phase 2, making every artefact byte-reproducible. Not a secure setup; `circuits/build/README.md` says so. |
| A-4 | proofs in vectors | Groth16 blinding scalars `(r, s)` are derived from `keccak256("MERCES_DEV_PROOF_RNG_V1" ‖ canonical inputs ‖ nonce)` so `pnpm vectors` is deterministic. The derivation includes the private salts, so proofs stay zero-knowledge towards verifiers; `proveReport(…, { deterministic: false })` gives CSPRNG randomness. |
| A-5 | groth16-solana `vk.rs` | `nr_pubinputs` is written as `IC.len()` (= public inputs + 1), the convention of the crate's own `parse_vk_to_rust.js`; the verifier only uses `vk_ic.len()`. `NR_PUBLIC_INPUTS = 6` is exported alongside. `proofA` in the vectors is already negated (`x ‖ q − y`); the program must not negate again. |
| A-6 | §5.2 `settle` vector step | One `settle` step = `begin_settlement(p)` + every `tally_bids` page + `finalize_settlement`; one `process_bid` step per bidder = `claim_win` (push). The simulator asserts the whole `settle` reverts atomically on `InvalidClearingPrice`. |
| A-7 | §5.3 `claim_release` | Zero releasable amount reverts with `NothingToRelease`; releases are blocked until `RaiseMintFinalized` (`MintNotFinalized`). |
| A-8 | §5.3 settlement | `settlement_ts` is the block time of the successful `finalize_settlement`; `first_period = period_of(settlement_ts)`; `cap_per_unit` is computed then and recomputed on `amend_terms` (cap multiple can only fall). |
| A-9 | §6.2 step 7 | Tier 1 and tier 4 reports carry no attestation; a supplied one is ignored. Tier 2 requires an active verifier key, tier 3 an active attestor. The simulator models "signature by registered key X" by actor name; harnesses sign the §1.4 message with the key derived from the vector's `keys[X].seed` (`deriveTestPrivateKey`). |
| A-10 | §6.2 step 4 | A fallback signature supplied while the accumulator average is valid is rejected (`FxFallbackNotAllowed`); a missing one when `NeedsFallback` is `FxFallbackRequired`. The rate carried by a fallback report is whatever the attestor signed (the vector states it). |
| A-11 | §6.6 checkpoints | Implemented literally: a period checkpoint is created by the first snapshot inside that period; `quarter_average(p)` needs checkpoints `p` and `p+1`. A quarter followed by a quarter with no snapshots at all is `NeedsFallback` (it would be anyway for `p+1`). |
| A-12 | §6.6 on Solana | The cross-check feed is modelled as an optional second normalized rate on the snapshot step (`crosscheckPrice/Expo`); pairs created with `crosscheck: false` ignore it (ASSUMPTIONS A21). |
| A-13 | §6.9 | `extinguish` on a Redeemed series inside its tail ends the tail; final distribution weights use `redeemed_units`. `claim_final` pays pending payouts + the final share and burns remaining units. `extinguish` when nothing is unreleased still marks the series Extinguished. |
| A-14 | §6.7 | `claim_redemption` records `redeemed_units` the first time a holder with units claims; later `claim_tail` uses that figure. Pending payouts are paid together with the redemption price. |
| A-15 | §7 `open_window` | All preconditions other than `WindowsDisabled`, `LockupActive` and `WindowOpen` revert with the single error `WindowNotEligible`. |
| A-16 | §7 `process_orders` vector step | One step processes every order and the dust pass; buyers must still be allowlisted and under the cap at fill time (`NotAllowlisted`, `WalletCapExceeded`). |
| A-17 | §11 | Error names used by `expect_revert` are the canonical list in `@merces/sdk` `errors.ts` (exported, with one-line meanings) and in `packages/vectors/README.md`. Chains map their own codes to these names. |
| A-18 | §11 | `expect` snapshots list every actor's stablecoin balance (and unit balance for the step's series), the series' treasury / vault / auction-escrow / window-escrow balances, the global fee collector and a fixed `ledger` view (field list in `packages/vectors/schema.json`). Harnesses assert every field present. |
| A-19 | §11 keys | Attestor / verifier keys are secp256k1 test keys derived as `keccak256("MERCES_TEST_KEY" ‖ seed) mod (n−1) + 1`; the vector lists seed, private key and address. Bid salts and Poseidon salts derive from the vector name. Nothing in the vectors is a secret. |
| A-20 | §6.2 step 8 | Router credit is consumed before the due amount is computed (`credit_used = min(router_credit, payment_usd)`); a report whose due is zero is paid on acceptance (`last_paid_period = period`). |
| A-21 | §6.4 | `expect.ledger.pausedTotal` reports `paused_total + pause_elapsed(now)` (time stopped so far, including an open pause) so the figure is meaningful mid-pause. |
| A-22 | brief C8 §6 (true-up) | `submit_trueup` / `pay_trueup` are implemented in the simulator (positive adjustments accrue after `attestation_ts + 60 d`, negative ones credit `router_credit`); no parity vector exercises them yet. |
